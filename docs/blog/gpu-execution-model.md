这是我学习 CUDA 过程中的一份笔记，写给同样在入门的读者，不是教程也不是权威参考。

### 1.1 测量前必须做的两件事

**一、插电。**

笔记本不插电会降频，这是正常行为。判据是跑负载时看显存时钟：

```
空闲：405 MHz      <- 省电降频，正常
满载：5000 MHz     <- 插电后应该看到这个
```

如果跑负载时还是 405 MHz，测出来的数字全都偏低。

**二、等它升频。**

GPU 不会一开跑就到最高频率。我第一次测 FP32 峰值时直接开测，得到 1773 GFLOPS；改成先持续烧 1.5 秒把频率拉满再计时，变成 3112 GFLOPS——**差将近一倍**。

所以下面用到的每个测量程序，内部都会先热身够时间才开始计时。这一步不能省。

## 2. 结论

从最小的单位往外走：**thread 是执行的最小单位，warp 是硬件的打包方式，warp 调度器负责发指令，ALU 负责执行，block 和 SM 是两层容器**——一层是你划的，一层是硬件的。

### 2.1 thread —— 执行的最小单位

你写一个 kernel，每个 `threadIdx` 对应的就是一个 thread：一个独立的执行流，有自己的寄存器和程序计数器。

**它不能和别的 thread 通信。** 没有「读另一个 thread 的变量」这种操作，也没法直接同步。

### 2.2 warp —— 硬件把 32 个 thread 绑成一包

这个打包是**硬件做的，你控制不了**。给 160 个 thread，硬件自己划成 5 个 warp。

绑在一起之后就有个后果：**同一个 warp 的 32 个 thread 共用一条指令**。你写 `if (threadIdx.x < 16) { ... }` 时，32 个 lane 还是得一起把这段代码走一遍，只是另外 16 个不写结果。这就是「warp 发散」的来源。

本机 warp 大小 = 32。这个数字在所有 CUDA 设备上都是 32，是 CUDA 体系决定的，不随 GPU 硬件条件变化的固定值。

### 2.3 warp 调度器 / warp 分区 —— 每周期挑一个 warp 发一条指令

调度器手里有一把 warp。每个周期它挑一个出来，发一条指令给它执行；下一个周期再挑一个（可以是同一个，也可以是别的）。

一个warp分区和一个warp调度器是一一对应的。

**手里有多少个 warp 是不固定的**，它是两个数相除：

```
每个调度器管的 warp 数 = 每 SM 最多 warp 数 ÷ SM 内的调度器数
```

两个数都随架构变。本机的每 SM 上限是 32 个 warp，调度器数量我实测没能确定，推测是 4 个——这两个数后文都会实测。

调度器的核心价值在**切换不要钱**：它这周期发现某个 warp 还在等内存，就直接换成另一个 warp 发指令，不需要保存/恢复任何上下文。所以「用一个 warp 的空档去填另一个 warp 的等待」是免费的。这也是为什么同 SM 中，warp越多，可能更能掩盖 warp 的等待时间。

### 2.4 ALU —— 真正执行指令的地方

warp 拿到指令后，由一堆 ALU 并行算它的 32 个 lane。

**但 ALU 的数量不一定等于 32。** 本机每 SM 有 64 个 FP32 单元（实测）。按上面「4 个子分区」的推测分下去就是每个子分区 16 个，一条 warp 级的 FMA 要花 **2 个周期**才算完，即先算 lane0-15，再算16-31。

这对你是透明的，但你算性能天花板时要用到：

```
本机每 SM 每周期 64 个 FP32 FMA  →  FP32 峰值 3112 GFLOPS
```

这个数字是所有计算型 kernel 的上限，后面反复用到。

### 2.5 block —— 一组 warp，绑定在同一个 SM 上

这是**你能控制的第一个层级**。`<<<grid, block>>>` 里的 `block` 就是它。

一条硬性规定：**一个 block 里的所有 warp 一定在同一个 SM 上**。这不是优化，是 CUDA 的承诺——正因为这条承诺，block 内的 thread 才能用共享内存互相通信、用 `__syncthreads()` 互相等待。如果 block 会跨 SM，这两样东西都不成立。

上限是 1024 个 thread。这个数字和「每 SM 最多 1024 个 thread」**是两条独立的约束**，只是在这台机器上恰好相等——换个架构就不相等了。

### 2.6 SM —— 硬件封装

一个 SM 大致长这样：

```
┌──────────────── SM ────────────────┐
│  寄存器文件    共享内存 / L1         │
│                                    │
│  ┌─ 子分区 ─┐ ┌─ 子分区 ─┐ ...      │
│  │ warp调度器│ │ warp调度器│         │
│  │   ↓      │ │   ↓      │          │
│  │ 16 个 ALU│ │ 16 个 ALU│          │
│  └──────────┘ └──────────┘          │
└────────────────────────────────────┘
```

本机有 **14 个** SM。你没法直接指定「用几个 SM」，只能通过 grid 的大小间接影响——block 够多，14 个才会都被点亮。

### 2.7 grid —— 一组 block，彼此不同步

grid 就是一组 block，散布在所有 SM 上。它和 block 有个关键区别：

> **block 内的 warp 能互相通信（共享内存 + `__syncthreads()`），block 之间不能。**

两个 block 之间没有任何直接的同步或通信手段，只能靠显存交换数据，而且得靠「kernel 结束」当分界线。本文不展开，但这一条决定了很多 kernel 得拆成好几次启动。

### 2.8 一张表看全

| 层                    | 是什么                       | 本机数量         | 你需要操心什么                          |
| --------------------- | ---------------------------- | ---------------- | --------------------------------------- |
| **thread**      | 执行的最小单位               | 你写多少有多少   | 逻辑写对、别越界                        |
| **warp**        | 32 个 thread，硬件绑死       | 按 32 自动分组   | **发散**——32 个 lane 是一起走的 |
| **warp 调度器** | 每周期挑一个 warp 发一条指令 | 每 SM 若干个     | 不用管                                  |
| **ALU**         | 真正执行指令的单元           | 每 SM 64 个 FP32 | 不用管，但性能上限由它定                |
| **block**       | 一组 warp，必在同一个 SM 上  | `blockDim`     | 大小（影响占用率）+ 边界判断            |
| **SM**          | 物理封装                     | 14 个            | grid 要够大，14 个才会被点亮            |
| **grid**        | 一组 block，互不同步         | `gridDim`      | 大小，别超`gridDim` 上限              |

## 3. 相关参数，以及怎么获取

要在自己卡上验证上面的结论，得先把参数拿全。这些参数分成三类，**获取方式完全不一样**。

### 3.1 第一类：CUDA 直接告诉你

`cudaDeviceGetAttribute` 一条命令就能拿。这台机器上的值：

| 参数                                 | 值                         | 属于哪一层  |
| ------------------------------------ | -------------------------- | ----------- |
| `warpSize`                         | 32                         | warp        |
| `MaxThreadsPerBlock`               | 1024                       | block       |
| `MaxThreadsPerMultiProcessor`      | 1024                       | SM          |
| `MultiProcessorCount`              | **14**               | SM          |
| `MaxRegistersPerMultiprocessor`    | 65536                      | SM          |
| `MaxSharedMemoryPerMultiprocessor` | 64 KB                      | SM          |
| `MaxSharedMemoryPerBlock`          | 48 KB                      | block       |
| `MaxBlocksPerMultiprocessor`       | 16                         | SM          |
| `MaxBlockDimX / Y / Z`             | 1024 / 1024 / 64           | block       |
| `MaxGridDimX / Y / Z`              | 2147483647 / 65535 / 65535 | grid        |
| `L2CacheSize`                      | 1024 KB                    | （SM 之外） |
| `GlobalMemoryBusWidth`             | 128 bit                    | —          |
| `MemoryClockRate`                  | 5001 MHz                   | —          |

最后三行拼一下就是显存带宽，要自己乘（DDR 所以乘 2）：

```
2 × 5001 MHz × 128 bit / 8 = 160 GB/s
```

### 3.2 第二类：CUDA 不告诉你，只能实测反推

**这类最容易被忽略，但本文大部分结论都来自它们。**

**ALU 数量。** 没有任何 API 能查「这张卡有几个 FP32 单元」，只能测峰值倒推：

```
ALU 数 = 实测 GFLOPS / (满载频率 GHz × 2)
                                              ↑ 一次 FMA = 乘 + 加 = 2 个浮点运算
```

这个公式要用**满载频率**，而 `cudaDevAttrClockRate` 返回的是**基础频率**（本机 1155 MHz，满载是 1740 MHz），差 1.5 倍。满载频率只能一边跑 kernel 一边用 `nvidia-smi` 读。

测量程序是一个纯 FMA 的 kernel。有两个设计要点：

- **每个线程跑两条互相独立的 FMA 链。** 只跑一条的话，循环里每次迭代都要等上一次算完，ALU 喂不满，测出来偏低。
- **计时前先持续烧 1.5 秒把频率拉满。** 直接开测时 GPU 还没升到满载频率，读数会低将近一半（1773 vs 3112 GFLOPS）。

本机实测：

```
实测 FP32 峰值            3112 GFLOPS
÷ 2 (FMA = 2 个浮点运算)  1556 GFMA/s
÷ 满载频率 1.74 GHz         894 个 FP32 单元
÷ 14 个 SM                  64 个 / SM
```

**warp 调度器数量。** 同样没有 API。测法是固定每 SM 的 block 数、只改 `blockDim`，看每 SM 放几个 warp 时 ALU 吞吐不再上涨。本机的曲线是：

```
   1 个 warp/SM     19.6%     <- 一条独立指令链填不满
   2 个             39.1%
   4 个             78.2%     <- 增长开始变缓
   8 个             99.3%     <- 基本吃满
```

线性段结束在 4 附近，据此**推测**是 4 个调度器。但这只是推测——曲线的形状区分不了「4 个调度器 × 16 个 ALU」和「2 个 × 32 个」，两种布局的预测完全一样。后面用到这个数时会再说明。

### 3.3 第三类：取决于你的 kernel，不是卡

前两类是**卡的属性**——同一个参数换张卡就变。这一类反过来：**同一张卡上，换个 kernel 就变。**

| 参数                   | 怎么拿                                              |
| ---------------------- | --------------------------------------------------- |
| 寄存器用量             | `cudaFuncGetAttributes().numRegs`                 |
| 每 SM 能驻留几个 block | `cudaOccupancyMaxActiveBlocksPerMultiprocessor()` |
| 实际占用率             | 上面那个数 ×`blockDim` ÷ 每 SM 线程上限         |

这三个数决定你的 kernel 实际能用上多少硬件。同一个 SM 上，寄存器用 64 个的 kernel 能塞 1024 个线程，用 105 个的只能塞 512 个——**卡一样，kernel 不一样，结果差一倍。**

上面这些测量都在 [`benchmarks/gpu-specs/`](../../benchmarks/gpu-specs/)：

```bash
cd benchmarks/gpu-specs
make run
```

| 文件             | 测什么                                                        | 覆盖哪一层        |
| ---------------- | ------------------------------------------------------------- | ----------------- |
| `specs.cu`     | 第一类参数全表 + block 落到哪个 SM                            | SM / block / grid |
| `flops.cu`     | 第二类：FP32 峰值 → ALU 数量，外加「几个 warp 才够」的曲线   | ALU / warp 调度器 |
| `stride.cu`    | 显存带宽、L2 命中、跨步访问                                   | 缓存层次          |
| `bank.cu`      | 共享内存的 bank 冲突                                          | 共享内存          |
| `occupancy.cu` | 第三类：寄存器和共享内存怎么限制占用率                        | block             |
| `sched.cu`     | 调度开销：block 的边际成本（能测）+ warp 切换的零开销（反证） | block / warp      |

## 4. 调度开销：block 和 warp 各要花多少

写 CUDA 时很容易起两个疑虑：

- grid 开几千上万个 block，**调度它们**是不是有开销？
- warp 那么多，每周期切来切去，**切换本身**是不是也有开销？

答案不一样：**一个可以不管，另一个根本不用管。**

### 4.1 block 调度：可以不管

测法很土：**用一个什么都不干的空 kernel，只改 block 数量，看耗时怎么涨。**

```cuda
__global__ void empty() {}
```

扫一组 grid 大小，每个点跑几千次取平均。测之前先用别的 kernel 把频率拉满，否则 GPU 还在低频，数字全部偏低。

| block 数       | 耗时 (µs)      | 每 block 边际成本 |
| -------------- | --------------- | ----------------- |
| 1              | 8.24            | —                |
| 56             | 11.48           | 59 ns             |
| 1024           | 11.84           | 3.5 ns            |
| **4096** | **12.35** | **1.0 ns**  |
| 16384          | 38.12           | 1.8 ns            |
| 65536          | 148.66          | 2.1 ns            |
| 262144         | 575.54          | 2.2 ns            |
| 1048576        | 2283.20         | 2.2 ns            |

两件事要分开看：

1. **1 个 block 就要 8.24 µs。** 这是主机侧把 kernel 塞进队列的成本，**跟 block 数量无关**——你开 1 块还是 1 百万块，这 8 µs 都要付。
2. **大 grid 区的边际成本约 2.2 ns/block**，而且要到 **6.5 万块以上**才看得出来。4096 个 block 那一档的边际成本只有 1.0 ns。

```
4096 个 block 多花的钱 = 12.35 - 8.24 ≈ 4.1 µs
```

对上一个动辄几百微秒的 kernel，**这是可以直接忽略的量级**。而且这还是在**空 kernel** 上测的——没有计算可以重叠，调度成本裸露在外。真实 kernel 里 block 调度和计算是重叠的，实际更收不到这笔钱。

所以**6.5 万块以下不用管 block 数，而实际应用中实际也用不到那么多block。**

### 4.2 warp 切换：不用管

这个给不出数值，因为它**不是一个耗时**。

block 调度是个**事件**：work distributor 把 block 分给 SM，中间有握手，能计时。

warp 切换不是事件，是调度器**每周期做选择时的一个选项**。它不是「先花 N 纳秒切过去，再发射」，而是「这一周期我选 warp 7 发射」——选谁都是同一个周期，**没有额外的一步**。所以没有「切换耗时」这个东西可以量。

那「没有开销」这个结论是怎么来的？**用理论上限反证：**

```
每 SM 每周期 64 个 FP32 FMA      <- 由 ALU 数量算出的上限
实测峰值 3112 GFLOPS
  = 3112e9 ÷ 2 ÷ 1.74e9 ÷ 14 ÷ 32
  = 2.00 条 warp-FMA / SM / 周期
```

**正好等于理论值 2.0，一点没少。**

如果每次 warp 切换要花一个周期，8 个 warp 交替发射就不可能跑满——切换的开销一定会吃掉一部分。跑满了，说明这条路上**没有可观测的损耗**。

严格说，这里能证明的是「warp 切换不产生可测的吞吐损失」。「零开销」是个简化说法——因为同一个周期里调度器本来只做一次选择，压根没有「切换」这个动作可以花时间。

### 4.3 一句话对比

|                      | 能不能测             | 量级                      | 要不要管           |
| -------------------- | -------------------- | ------------------------- | ------------------ |
| **block 调度** | 能                   | ~2 ns/block（大 grid 区） | 6.5 万块以下不用管 |
| **warp 切换**  | 不能（不是一个动作） | 无                        | 完全不用管         |

测量代码在 [`benchmarks/gpu-specs/sched.cu`](../../benchmarks/gpu-specs/sched.cu)。

## 5. GPU 执行模型的理解应用

回头解决开头的 bank 冲突的问题，再加一个模型能直接解释的现象。

### 5.1 bank 冲突是哪个层级的

答案要拆成两件事，混在一起想就会绕不出来：

|                     | 层级               | 为什么                                                       |
| ------------------- | ------------------ | ------------------------------------------------------------ |
| **共享内存**  | **block 级** | 每个 block 一块自留地，只有 block 内的线程能访问             |
| **bank 冲突** | **warp 级**  | 硬件每次只把**一个 warp 的 32 个请求**送进共享内存单元 |

第二行直接来自「**warp 是指令发射的单位**」。硬件每次发射一条指令，对象就是一个 warp——共享内存的访问也是这么发出去的：

```
warp 调度器 ──发出 LDS 指令──► LSU（访存单元）──► 32 个 bank
     ↑                              ↑
  只管发射这一件事            在这里分析 32 个地址、决定分几拍
```

**调度器不知道也不关心你要访问哪个 bank。** 它手里只有「发射」这一件事。按 bank 拆成几拍，是 LSU 收到指令之后的事——

> 一条访存指令里如果撞了 bank，LSU 就得把它**拆成多拍**再送给共享内存单元。原本一拍能发完的请求变成四五拍，这个 warp 的这次访存就变慢了。

这里要注意：**共享内存是片上的 SRAM，在 SM 内部，不是 DRAM。** 这正是它存在的理由——如果它在 DRAM 里，那它和全局内存就没区别了。「拆成多拍」发生在 LSU 到共享内存单元这一段，全程都在片上。

这就解释了为什么**跨 warp 不算冲突**：两个 warp 各自访问 bank 0 时，它们的指令由调度器在**不同周期**发出去，天然错开。如果判定单位是 block，这两个 warp 就会互相干扰——但硬件一次只看一个 warp 的 32 个请求。

实测（一个 warp 反复读 `buf[t * stride]`）：

```
  stride   地址模式    冲突倍数     耗时(ms)   相对 s=1
       0   全部同一地址       1       0.782    （广播，免费）
       1   连续(0..31)        1       0.784     1.00x
       2          跨步       2       0.747     0.95x   <- 小冲突被并行度掩盖了
       4          跨步       4       1.479     1.89x
       8          跨步       8       2.955     3.77x
      16          跨步      16       5.890     7.51x
      32          跨步      32      11.812    15.06x   <- 慢 15 倍
```

三个读法：

- **stride=0 是广播**：32 个线程读同一个32位字，硬件直接广播，**和连续访问一样快**。这是共享内存独有的福利，显存没有。
- **stride=2 没变慢**：确实有 2 路冲突，但同 SM 上还有别的 warp 能顶上（见下一小节）。**小冲突不一定要治，大的必须治。**
- **stride=32 慢 15 倍**：地址全是 `32t`，bank 全是 `32t % 32 = 0`，32 个线程挤在一个 bank 上。

最经典的例子是矩阵转置。`__shared__ float tile[32][32]`：

```cuda
// 写入：线程 (tx,ty) 写 tile[ty][tx]
//   字地址 = ty*32 + tx  ->  bank = (ty*32+tx) % 32 = tx
//   warp 里 tx=0..31 -> bank 0..31 -> 无冲突 ✓

// 读出：线程 (tx,ty) 读 tile[tx][ty]      <- 转置就发生在这一步
//   字地址 = tx*32 + ty  ->  bank = (tx*32+ty) % 32 = ty
//   warp 里所有线程的 ty 是同一个值！
//   -> 32 个线程全撞在 bank ty 上 -> 32 路冲突 ✗
```

**写入没事，读出崩了。** 因为转置的本质就是换维度访问，这一步正好把「分散」变成了「聚集」。

治法是把数组宽度多加 1，改成 `tile[32][33]`：

```
读出 tile[tx][ty]：字地址 = tx*33 + ty
              bank = (tx*33 + ty) % 32 = (tx + ty) % 32
              tx = 0..31 -> bank = ty, ty+1, ..., ty+31  ->  32 个不同 bank ✓
```

**加 1 个元素，每一行就相对上一行错开一个 bank**，原来「上下对齐」的列访问被打散成「斜着排」。看起来像玄学，上面两行算术就是它的全部道理。

### 5.2 单 SM 的 warp 数量对性能的影响

同一个 kernel，把每 SM 的 warp 数从 1 加到 8，快 5 倍：

```
   1 个 warp/SM     19.6%
   2 个             39.1%
   4 个             78.2%
   8 个             99.3%     <- 基本吃满
```

原因就在**warp 切换不要钱**。

```
周期 1:  warp A 的 FMA 发出去了，结果要等 4 个周期才回来
周期 2:  调度器看 A 还没回来 —— 换成 warp B 发指令
周期 3:  换成 warp C
周期 4:  换成 warp D
周期 5:  A 的结果回来了，又能发它
```

SM 上只有 1 个 warp 的话，第 2 到第 4 个周期调度器无事可做，**ALU 就在空转**。多放几个 warp，就是拿它们的指令去填这些空档。

#### 5.2.1 但填满了就不会再涨

上面那张表最后是平的——8 个 99.3%，32 个还是 99.3%。这不是测量噪声，是**到顶了**。

这里要分清两件很容易混起来的事：

| | 是什么 | 加 warp 有用吗 |
| --- | --- | --- |
| **延迟** | 一个请求发出去，到数据回来要多久 | **有用**——warps 少的时候没人填这些空档 |
| **吞吐** | 每周期能发出多少请求、搬回多少字节 | **没用**——这是固定容量 |

**多 warp 掩盖的是「延迟」，不是「吞吐」。** LSU 和 DRAM 的吞吐都是固定的：LSU 每周期能处理的请求数、DRAM 每周期能搬的字节数，**不会因为 warp 变多而变大**。warp 的作用只是让这些固定容量别闲着——填满了就到顶。

所以曲线其实分两段：

| 区间 | 谁在限制 | 加 warp |
| --- | --- | --- |
| 8 个 warp 以下 | 空档没人填，LSU / DRAM 还没跑满 | 接近线性 |
| 8 个 warp 以上 | LSU / DRAM 的吞吐到顶 | **纯排队，不再涨** |

**「warp 越多越好」和「warp 多了也没用」都对**，只是说的曲线上的不同区间。判断自己在哪一段，看加 warp 之后吞吐还涨不涨就行。


**但「几个才够」不是一个硬件常数。** 它等于「你的 kernel 要等多久」：

| kernel 类型      | 在等什么                        | 需要多少 warp/SM           |
| ---------------- | ------------------------------- | -------------------------- |
| 纯计算、依赖链短 | ALU 发射                        | 少（上面那张表就是这一类） |
| 纯计算、依赖链长 | ALU 延迟（几周期）              | 中                         |
| 访存受限         | DRAM 延迟（**几百周期**） | **远多于计算型**     |

同样是「加 warp」，两种 kernel 的收益完全不同。实测对照：

| 测量                                                      | 结果                                       | 原因                                                   |
| --------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------ |
| 纯 ALU 循环：`<<<14,256>>>` vs `<<<14,1024>>>`        | **一样快**（21.4 vs 21.3 ms）        | ALU 延迟只有几周期，8 个 warp 就盖住了，加到 32 个没用 |
| saxpy（访存受限）：`<<<14,256>>>` vs `<<<4096,256>>>` | 慢了**1.57 倍**（139.2 vs 88.7 µs） | 访存延迟几百周期，256 线程/SM 根本盖不住               |

所以上面那张 warp 数的表，**是「这一次实验的记录」，不是「你这张卡需要多少个 warp」**。判断自己的 kernel 该放多少 warp，要先看它在等什么。

最后补一句：**warp 也不是想加就能加的。** 上面那些是「放几个 warp 才喂得满」，但一个 SM 上实际能同时驻留多少 warp，还要看寄存器、共享内存、每 SM 的 block 数上限——这几条任何一条都能先把位置占掉。那是另一个话题了。
