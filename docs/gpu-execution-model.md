## 0. 一句话模型

> **warp 是「指令发射」的单位，block 是「共享内存和同步」的单位，SM 是「物理资源」的单位。**
>
> 线程你随便写，硬件按 32 个一组打包成 warp；warp 被整块塞进某个 SM；SM 上能同时住几个 block 由硬件决定。

后面所有内容都是这句话的展开。

---

## 1. 层级总览

### 1.1 总表

**从底（硅）到顶（你写的代码），它们是这样叠起来的：**

```
    ┌────────────────────────────────────────────────┐
    │  grid      一组 block，散布在所有 SM 上           │  ← 你指定
    │  block     一组 warp，必须落在同一个 SM 上        │  ← 你指定
    │  warp      32 个线程，硬件绑死成一个调度单位      │  ← 硬件打包
    │  thread    一个执行流                            │  ← 你写
    ├──────────────── 软件 / 硬件 分界 ───────────────┤
    │  SM        4 个子分区 + 寄存器文件 + 共享内存/L1  │  ← 硬件
    │  子分区     1 个 warp 调度器 + 16 个 ALU         │  ← 硬件
    │  ALU       真正做浮点运算的单元                   │  ← 硬件
    └────────────────────────────────────────────────┘
```

| 层 | 是什么 | 本机数量 | 谁决定 |
| --- | --- | --- | --- |
| **ALU（FP32 单元）** | 真正做浮点运算的硬件，一个周期算一个 32 位浮点 | 每 SM **64** 个 | 硬件 |
| **子分区 / warp 调度器** | 每周期挑 1 个 warp 发 1 条指令；下辖 16 个 ALU | 每 SM **4** 个 | 硬件 |
| **SM** | 物理封装：4 个子分区 + 65536 个寄存器 + 64KB 共享内存 | 全卡 **14** 个 | 硬件 |
| **thread** | 一个执行流 | 你写多少有多少 | **你** |
| **warp** | 32 个线程，硬件绑死成一个调度单位 | 创建时按 32 自动分组 | **硬件自动** |
| **block** | 一组 warp，**必须在同一个 SM 上**（所以能用共享内存互相通信） | `blockDim` | **你** |
| **grid** | 一组 block，**彼此之间不能同步**（只能靠显存 + kernel 边界交接） | `gridDim` | **你** |

注意最后三行的「谁决定」：**warp 是硬件自己打包的，你控制不了**；block 和 grid 的分法才是你写的。

### 1.2 几个容易忽略的点

**① warp 你指定不了。** 你没法说「我要 5 个 warp」——你给 160 个线程，硬件划成 5 个 warp。这是为什么 `blockDim` 取 32 的倍数不浪费：取 100 会得到 4 个 warp（3 个满 + 1 个只有 4 个线程在干活，另外 28 个 lane 空转）。

**② block 不跨 SM。** 实测：

```
block 0 的 warp 0,1,2,3   ->   全在 SM 0 上
block 1 的 warp 0,1,2,3   ->   全在 SM 2 上
block 2 的 warp 0,1,2,3   ->   全在 SM 4 上
block 3 的 warp 0,1,2,3   ->   全在 SM 6 上
```

一个 block 的所有 warp 必在同一个 SM；不同 block 分散到不同 SM。**共享内存能生效，前提就是这个**——如果 block 的 warp 散在多个 SM 上，它们就没法共享片上内存了。

**③ grid 内部完全没有同步机制。** block 之间没有任何直接通信手段，只能通过**显存**交换数据：上一个 kernel 把结果写进显存，下一个 kernel 再读出来。

这里要纠正一个常见误解：`cudaDeviceSynchronize()` **不是 block 之间的通信机制**，它是**主机侧**的 API——让 CPU 停下来等设备干完活。真正的保证来自**同一个 stream 上的顺序性**：排在同一队列里的 kernel，前一个不跑完后一个不会开始。

所以只写 kernel、不在 CPU 上读结果时，**你不需要任何 `cudaDeviceSynchronize`**，数据照样正确交接。

**④ warp 到 SM 内部子分区的分配是静态的。** block 启动时硬件就把每个 warp 钉在某个子分区上，之后不换。

## 2. SM 内部

### 2.1 结构

```
                    ┌─────────────── SM（本机 14 个）───────────────┐
                    │                                              │
                    │  寄存器文件   65536 个 32 位                   │
                    │  共享内存/L1  64 KB（其中共享内存最多 48KB/block）│
                    │                                              │
                    │  ┌── 子分区 0 ──┐ ┌── 子分区 1 ──┐ ... 共 4 个  │
                    │  │ warp 调度器  │ │ warp 调度器  │            │
                    │  │     │        │ │     │        │            │
                    │  │ 16 个 FP32   │ │ 16 个 FP32   │            │
                    │  └──────────────┘ └──────────────┘            │
                    │                                              │
                    │  访存单元（LSU）：load/store 从这里出去          │
                    └──────────────────────────────────────────────┘
```

### 2.2 你这张卡的实际数字

| 项 | 值 | 怎么来的 |
| --- | --- | --- |
| SM 数量 | **14** | `cudaDevAttrMultiProcessorCount` |
| 每 SM 最多线程 | **1024** | `cudaDevAttrMaxThreadsPerMultiProcessor` |
| 每 SM 最多 warp | **32** | 1024 / 32 |
| 每 block 最多线程 | **1024** | `cudaDevAttrMaxThreadsPerBlock`——**和上一行是两条独立约束**，见 §5 |
| 每 SM 最多 block | **16** | `cudaDevAttrMaxBlocksPerMultiprocessor` |
| 每 SM 的 FP32 单元 | **64** | **实测反推**，见 §6.2 |
| 每个子分区的 FP32 单元 | **16** | 见下面的说明 |
| 每 SM 每周期能算 | **64 个 FP32 FMA** | = 4 × 16 |
| FP32 峰值 | **3112 GFLOPS** | 64 × 14 × 1.74 GHz × 2 |

**关于 `/16` 这个数字，必须说明白：**我实测能确定的只有「每 SM 64 个 FP32 单元」。至于这 64 个怎么分区，我的实验**区分不出来**——

| 布局 | 峰值 | 单 warp 效率 | 饱和点 |
| --- | --- | --- | --- |
| A：4 分区 × 16 ALU，warp-FMA 花 2 周期 | 2 条指令/周期 | 25% | 4 个 warp |
| B：2 分区 × 32 ALU，warp-FMA 花 1 周期 | 2 条指令/周期 | 25% | 4 个 warp |

两者预测完全一样，吞吐扫描分辨不了。**表格里的「4 分区 × 16」来自 Turing 架构的官方布局，不是实测结论。**

### 2.3 为什么 32 个线程的 warp 只配 16 个 ALU

因为 **一个 warp 的 32 个 lane 不是同一周期算完的**：

```
周期 1:   lane 0  1  2 ... 15     ← 占用 16 个 ALU
周期 2:   lane 16 17 18 ... 31    ← 占用同样那 16 个 ALU

一个 warp-FMA 指令 = 2 个周期
```

**「warp = 32 线程」是软件模型的约定（SIMT），不是硬件的执行宽度。** 硬件负责把这道缝抹平，你写代码时永远按「32 个线程一起干活」思考就行。

对比：

| | 每分区 FP32 | warp-FMA 周期数 | 峰值（每 SM 每周期） |
| --- | --- | --- | --- |
| **GTX 1650（TU117）** | 16 | **2** | 64 个 FMA |
| RTX 30/40 系（GA10x/AD10x） | 32 | 1 | 128 个 FMA |

## 3. 同一时间什么在工作

### 3.1 延迟隐藏

- 一个 SM 上可以同时驻留**多个 block、多个 warp**（本机每 SM 最多 32 个 warp）
- 但**每个 warp 调度器每周期只发射 1 条指令**
- 真正并行的是**多个 warp**；每个 warp 内部是「一条指令管 32 个 lane」
- **warp 之间切换是零开销的**：调度器这周期发现 warp 3 的访存还没回来，就直接发射 warp 7 的指令，不需要保存/恢复任何上下文

一句话：**为什么需要很多 warp？因为要用「别的 warp 有活干」来盖住「这个 warp 在等内存」。**

### 3.2 实测：几个 warp 才够

每 SM 放 1 个 block，blockDim 从 32 加到 1024：

```
  blockDim    warp/SM      GFLOPS   相对峰值
  --------------------------------------------------
        32          1       608.5      19.6%
        64          2      1215.8      39.1%
       128          4      2434.5      78.2%   ← 基本够了
       256          8      3090.0      99.3%
       512         16      3090.9      99.3%
      1024         32      3090.6      99.3%
```

读法：

- 1 个 warp 只发挥 **19.6%**，4 个到 **78.2%**，**8 个才到 99.3%**
- 4 个 warp 之后增长明显变缓，但**并没有饱和**——8 个 warp 才基本吃满
- 这不是「ALU 不够用」：ALU 总量是固定的，喂不喂得满取决于**有没有足够多能同时干活的 warp**

**但这个数字不能当成「每 SM 需要 8 个 warp」这种硬件结论。** 它只说明：**这个特定任务**需要 8 个 warp/SM 才能把它的等待时间盖住。换个任务，需要的 warp 数完全不一样——

| kernel 类型 | 瓶颈 | 需要多少 warp/SM |
| --- | --- | --- |
| 纯计算、依赖链短 | ALU 发射 | 少（本测试就是这一类） |
| 纯计算、依赖链长 | ALU 延迟（几周期） | 中 |
| 访存受限 | DRAM 延迟（**几百周期**） | **远多于计算型** |

所以这张表是**一次实验记录**，不是**硬件参数**。怎么把它用到自己的 kernel 上，见 §8。

## 4. 把模型复述一遍

下面这份是我自己复述的版本，逐条对照前面的内容。**对的打 ✓，要改的打 ✗ 并附修正。**

> **① 分区 = warp 调度器。**
>
> **✓ 对。** SM 内部切成若干子分区，每个子分区挂一个 warp 调度器。

> **② 一个 warp 调度器可以管很多个 warp，但同一时刻只能给一个 warp 发指令。**
>
> **✓ 对。** 本机每 SM 最多 32 个 warp，分到 4 个子分区，每个调度器管 8 个。
>
> 补一句：这个「管」是**静态**的——warp 在 block 启动时就被钉在某个子分区上，之后不换。不是「谁空闲就调度谁」。

> **③ 等指令回复的过程中，warp 调度器可以给其他 warp 发指令。**
>
> **✓ 对，这就是延迟隐藏的全部内容。** warp 切换在硬件层面是**零开销**的，不需要保存/恢复上下文。
>
> 关键推论：**所以「需要多少 warp」取决于「要等多久」**——等 ALU 几周期只要几个 warp，等 DRAM 几百周期就要几十个。这就是 §3.2 那张表真正的含义。

> **④ bank 冲突本质是 warp 调度器不能同时发「同 bank 但不同 32 位字」的请求，但能把「不同 bank 的不同 32 位字」打包。**
>
> **✗ 一半对，一半要改。**
>
> - 「同 bank 不同字 → 冲突」「不同 bank → 并行」这两句是对的。
> - **但打包/拆分的不是 warp 调度器，是 LSU（访存单元）。** 调度器只管把指令发出去，完全不知道你要访问哪个 bank；地址分析发生在 LSU 那一层。
> - 而且严格说不是「不能发」，是**发了之后硬件得分几次服务**。

> **⑤ block 永远不跨 SM。**
>
> **✓ 对。** 硬性规定。

> **⑥ 不同 block 只能通过 `cudaDeviceSynchronize` 来交流。**
>
> **✗ 说法要改。** `cudaDeviceSynchronize()` 是**主机侧** API——让 CPU 停下来等设备干完活。它**不是** block 之间的通信机制。
>
> 准确的说法：**block 之间没有任何直接通信手段，只能通过显存交换数据**；而「上一个 kernel 写完了没有」这件事由**同一个 stream 的顺序性**保证，**不需要显式 sync**。

> **⑦ 我的 GPU 是 14 个 SM，每个 SM 放 32 个 warp，这 32 个 warp 由 4 个分区（warp 调度器）管辖。**
>
> **✓ 对。** 14 SM、每 SM 1024 线程 = 32 warp、4 个子分区各 8 个。
>
> 唯一要留意的是「4 个分区」这条**我实测不出来**（见 §2.2）——实测能确定的只有「每 SM 64 个 FP32 单元」，而「4×16」和「2×32」两种布局的预测完全一样。4 分区 × 16 是 Turing 的官方布局，不是测量结论。

## 5. 五个常见误解

| 误解 | 实际 |
| --- | --- |
| 「`blockDim` 要大于 SM 数才能跑满」 | **错**。决定跑满的是 `gridDim`（block 个数）。`<<<1, 1024>>>` 的 blockDim 是 SM 数的 73 倍，但只点亮 1 个 SM |
| 「线程是逐个调度的」 | **错**。调度单位是 **block**，执行单位是 **warp**。100 万线程 = 4096 次 block 调度 + 32 个 warp 一组 |
| 「共享内存是 SM 级的」 | **错**。**内存本身是 block 级**（每 block 一块自留地），只有 block 内可见 |
| 「bank 冲突是整个 block 或整个 SM 的事」 | **错**。冲突判定是 **warp 级**，见 §7 |
| 「`cudaDeviceSynchronize` 是 block 之间通信用的」 | **错**。它是主机侧等待；block 之间靠**显存** + **同 stream 顺序**交接数据 |
| 「每 block 1024 线程是从『每 SM 1024 线程』推出来的」 | **错**。两条**独立**约束。A100/H100 每 SM 是 **2048** 线程，block 上限仍**是 1024**。你卡上两个数恰好都等于 1024，所以容易混 |
| 「占用率 = 1024 / blockDim」 | **错**。还要看寄存器、共享内存、每 SM 最多 block 数（你的卡是 **16**）。见 §6.5 |

## 6. 怎么测你这张卡的这些参数

代码在 [`benchmarks/gpu-specs/`](../benchmarks/gpu-specs/)，`make run` 一次跑完。

### 6.0 测量前提：先插电

**这是最容易毁掉全部数据的一件事。**

```bash
nvidia-smi --query-gpu=clocks.mem,clocks.sm --format=csv
```

- 空闲时 `clocks.mem = 405 MHz` 是正常的省电降频
- **满载时必须是 5000 MHz**，SM 频率 1740 MHz
- 如果满载时显存还是 405 MHz，就是在性能墙后面测，数字全部偏低

还有一个坑：**GPU 不会立刻升频**。直接开测的话它还在低频，实测差将近一倍（1773 vs 3112 GFLOPS）。所以 `flops.cu` 和 `stride.cu` 内部都会先**持续烧 1.5 秒**把频率拉满，再开始计时。

### 6.1 `specs.cu` — 能直接查到的

用 `cudaDeviceGetAttribute` / `cudaGetDeviceProperties`。本机结果：

```
SM 数量             14            <- 决定"最多点亮几个"
每 SM 最多线程      1024
每 SM 最多 warp     32            <- 1024 / warpSize
每 block 最多线程   1024
blockDim 上限       x=1024 y=1024 z=64
gridDim  上限       x=2147483647 y=65535 z=65535

共享内存 / block    48 KB
共享内存 / SM       64 KB
寄存器   / SM       65536 个 32 位
L2 缓存             1024 KB
常量内存            64 KB

显存                4096 MB，128 bit，5001 MHz  ->  理论 160.0 GB/s
SM 基础频率         1155 MHz      <- 不是满载频率！
```

顺带它还会打印 block 到 SM 的落位规律（`%smid` / `%warpid` / `%laneid` 内联汇编）。

**注意 `%warpid` 是「warp 在 SM 上的槽位号」**，不是稳定编号——文档明说它的值在执行期间可能变化。只能用来观察拓扑，不能拿它做跨 warp 的逻辑判断。

### 6.2 `flops.cu` — 查不到的必须测

**CUDA 没有任何 API 能告诉你这张卡有多少个 ALU**，只能测出来：

```
ALUS = 实测GFLOPS / (满载频率GHz × 2)
       ↑ ×2 是因为一次 FMA = 乘 + 加 = 2 个浮点运算
```

本机：

```
实测 FP32 峰值          3112 GFLOPS
用基础频率 1155 MHz 算   1347 个   <- 偏大，因为频率用错了
用满载频率 1740 MHz 算    894 个   <- 对
除以 14 个 SM            每 SM 64 个 FP32
```

**这里有个陷阱**：CUDA 查到的 `cudaDevAttrClockRate` 是**基础频率**，不是满载频率。用它算会得到 1347 这种荒谬的数字。满载频率只能一边跑 kernel 一边用 `nvidia-smi` 看。

测法：写一个纯 FMA 的 kernel，**两条独立链**（一条链会被延迟卡住），跑到频率稳定后计时。

### 6.3 `stride.cu` — 访存带宽的两个实验

**实验 A：数据装不装得进 L2（1 MB）**

总读取量固定 16 GB，只改数组大小：

```
  数组大小   扫描轮数     耗时(ms)     读取GB/s
       256 KB        61035          16.0        1001.8
      1024 KB        15258          14.5        1101.6   <- 刚好塞满 L2
      4096 KB         3814         144.0         111.1   <- 塞不下，每次去 DRAM
```

**1 MB 和 4 MB 之间差 10 倍，代码一个字没改。**

**实验 B：合并 vs 跨步**

元素数、线程数、总访存量全部固定，只改相邻线程的地址差 `s`：

```
    s    warp覆盖跨度   耗时(ms)   有效带宽   相对s=1
   1           124 B      0.248   135.4 GB/s     1.00x
   2           248 B      0.737    45.5 GB/s     2.98x
   4           496 B      1.489    22.5 GB/s     6.01x
   8           992 B      2.997    11.2 GB/s    12.10x
  16          1984 B      4.097     8.2 GB/s    16.53x
  32          3968 B      4.987     6.7 GB/s    20.12x
```

**s 从 1 到 32，带宽掉 20 倍。** 代码几乎没变，元素一个没少处理。

机制：硬件取数的最小单位是 **32 字节的扇区**。`s=1` 时 32 个线程要 128 字节连续数据 = 4 个扇区，利用率 100%；`s=32` 时 32 个线程散在 32 个不同扇区里，每个扇区只用到 4/32 = 12.5%，浪费 8 倍。

### 6.5 `occupancy.cu` — 占用率由什么限制

§6.1 说的是「上限是多少」，这一节说「上限是谁定的、什么情况下够不着」。

**四条独立的约束，任何一条都能成为瓶颈：**

| 约束 | 来源 | 本机数值 | 能驻留几个 block |
| --- | --- | --- | --- |
| 每 SM 线程数 | 硬件属性 | 1024 | `1024 / blockDim` |
| 寄存器文件 | 硬件物理 | 65536 个 32 位 | `65536 / (寄存器数 × blockDim)` |
| 共享内存 | 硬件物理 | 64 KB / SM | `64KB / 每 block 共享内存` |
| 每 SM 最多 block | 硬件属性 | **16** | 直接封顶 |

```
每 SM 能驻留的 block 数 = min(上面四个)
```

**所以光看 `blockDim` 算不出占用率。**

#### 实验 1：block 线程数超过上限

```
<<<1, 1024>>>  ->  启动成功
<<<1, 1025>>>  ->  invalid argument
<<<1, 2048>>>  ->  invalid argument
```

**硬报错，不会静默截断。** 而且这个错误是**同步返回**的——`cudaGetLastError()` 立刻拿得到，不像越界访问要 `synchronize` 之后才发现。

注意这个 1024 **不是从「每 SM 1024 线程」推出来的**，是两条独立约束（见 §5 那条误解）。

#### 实验 2：寄存器限制占用率

同一个循环体（96 个元素的数组全展开在寄存器里），只改寄存器预算：

```
kernel                       寄存器/线程   每 SM block   线程/SM
__launch_bounds__(1024, 1)            64             1    1024 (100%)
__launch_bounds__(256, 1)            105             2     512 (50%)
__launch_bounds__(128, 1)            105             4     512 (50%)
```

**同一个 kernel，寄存器从 64 涨到 105，占用率就从 100% 掉到 50%。**

验算：`105 × 256 = 26880`，`65536 / 26880 = 2.44` → 2 个 block ✓

**但第一行那个 100% 是虚的。** `__launch_bounds__(1024, 1)` 是在告诉编译器「我最多用 1024 个线程启动」，编译器就必须把寄存器压到 `65536 / 1024 = 64` 个以内——不够用只能 **spill**（把变量溢出到显存/local memory）。

**占用率上去了，每条指令却变慢了。** 这是「占用率越高越好」最典型的反例。所以看到 100% 占用率别高兴太早，先看 `cudaFuncGetAttributes` 报的 `numRegs` 和有没有 local memory 流量。

#### 实验 3：共享内存限制占用率

blockDim 固定 256、寄存器很少，只改每 block 申请多少共享内存：

```
每 block 共享内存   每 SM block   线程/SM   占用率
           0 KB             4       1024     100%
          16 KB             4       1024     100%
          24 KB             2        512      50%
          32 KB             2        512      50%
          48 KB             1        256      25%
```

**光靠共享内存就能把占用率从 100% 压到 25%**，寄存器一个没用多。

验算：`64 KB / 24 KB = 2.67` → 2 个 ✓

你 Week 4 写 tiled matmul 时会碰到这个：`__shared__ float As[32][33] + Bs[32][33]` 是 8448 字节，看着不多，但 tile 一开大很快就打到 48 KB 的单 block 上限，占用率就掉下去了。**tile size 不是越大越好，这是原因之一。**

## 7. 用模型解释 bank 冲突

### 7.1 什么是 bank

共享内存被硬件切成 **32 个 bank**。每个 bank 宽 4 字节，**每个时钟周期只能服务一次访问**。

```
bank 号 = (地址 / 4) % 32        // 除以 4 得到第几个 32 位字，再对 32 取余
```

连续的 32 个 float 恰好铺满 32 个 bank：

```
字地址:  [0]  [1]  [2]  [3] ... [31] [32] [33] ...
bank:     0    1    2    3  ...  31    0    1  ...
         └──── 一圈 32 个 ────┘  └── 又从头开始 ──
```

### 7.2 三种情况

一个 warp 的 32 个线程同时发出访问，硬件看它们落在哪些 bank：

| 情况 | 结果 |
| --- | --- |
| 32 个线程落在 **32 个不同的 bank** | 一次搞定 |
| 多个线程落在**同一 bank** 但**不同 32 位字** | **串行化**——冲突几路就多花几倍时间 |
| 32 个线程访问**完全同一个 32 位字** | **广播**，一次搞定（免费） |

### 7.3 为什么是 warp 级，不是 block 级或 SM 级

这是最容易搞混的地方，要分两层看：

| 东西 | 层级 | 原因 |
| --- | --- | --- |
| **共享内存这块内存** | **block 级** | 每个 block 一块自留地，只有 block 内的线程能访问 |
| **bank 冲突这个现象** | **warp 级** | 硬件每次只把**一个 warp 的 32 个请求**打包送进共享内存单元 |

```
warp 调度器  ──发射一条 LDS 指令──►  LSU（访存单元）  ──►  共享内存的 32 个 bank
   ↑                                      ↑
  只管发射这一件事                    真正在这里分析 32 个地址、决定分几拍
```

两个要点：

1. **调度器不知道也不关心你访问哪个 bank**。它只管发指令。地址冲突是 **LSU** 收到指令后，把 32 个地址摊开看落在哪些 bank 上，能一次服务完就一次，不能就**拆成几拍**。
2. **严格说不是「不能发」，是「发了之后硬件得分数次服务」**。从程序角度看是变慢，机制上是串行化。

**跨 warp 不冲突**：两个不同 warp 各自访问 bank 0，不算冲突——它们的请求由调度器在**不同周期**发出去，天然错开。

### 7.4 实测

一个 warp 的 32 个线程反复读 `buf[t * stride]`：

```
  stride   地址模式    冲突倍数     耗时(ms)   相对 s=1
       0   全部同一地址       1       0.782    (广播，免费)
       1   连续(0..31)        1       0.784     1.00x
       2          跨步       2       0.747     0.95x   <- 小冲突被并行度掩盖了
       4          跨步       4       1.479     1.89x
       8          跨步       8       2.955     3.77x
      16          跨步      16       5.890     7.51x
      32          跨步      32      11.812    15.06x   <- 慢 15 倍
```

三个读法：

- **stride=1**：地址 0..31 → bank 0..31，每个 bank 恰好一个线程 → 一次搞定
- **stride=32**：地址 0,32,64,...,992 → bank 全是 `(32t)%32 = 0` → 32 个线程全挤在 bank 0 → 32 路冲突
- **stride=0（广播）**：32 个线程读同一个字 → 硬件直接广播，**和连续访问一样快**（0.782 vs 0.784）
- **stride=2 没变慢**：确实有 2 路冲突，但 32 个 warp 里有别的 warp 顶上，被掩盖了。**小冲突不一定要治，大的必须治**

### 7.5 和显存的跨步访问是同一个道理

| | 显存 | 共享内存 |
| --- | --- | --- |
| 硬件资源单位 | **32 字节的扇区** | **4 字节的 bank** |
| 一个 warp 的请求 | 合并成尽量少的事务 | 落在 32 个 bank 上 |
| 资源挤占 | 多线程撞同一扇区 → 多事务 | 多线程撞同一 bank → 串行化 |
| 实测代价 | 最惨慢 **20 倍** | 最惨慢 **15 倍** |

**机制完全一样，只是单位从 32 字节换成了 4 字节。** 所以共享内存不是「随便跨步都没事」——它只是把惩罚从 32 字节粒度降到 4 字节粒度，**并且把地址映射规则交给你控制**。

### 7.6 判断自己的 kernel 有没有 bank 冲突

不用背规则，用这个算法：

1. 写下访问共享内存的那一行，比如 `s[threadIdx.x * k]`
2. 把 `threadIdx.x = 0,1,2,...,31` 代进去，算出 32 个**字地址**（float 数组的字地址就是下标）
3. 每个地址 `% 32` 得到 bank 号
4. **32 个 bank 号里出现重复，重复几次就是几路冲突**

验证：`s[t]` → `0,1,...,31` 全不同 → 没事。`s[t*32]` → 全是 0 → 32 路 → 得治。

### 7.7 经典案例：矩阵转置的 padding

```cuda
__shared__ float tile[32][32];      // 32x32 方块

// 写入：线程 (tx,ty) 写 tile[ty][tx]
//   字地址 = ty*32 + tx  ->  bank = (ty*32+tx) % 32 = tx
//   warp 里 tx=0..31 -> bank 0..31 -> 无冲突 ✓

// 读出：线程 (tx,ty) 读 tile[tx][ty]      <- 转置就发生在这一步
//   字地址 = tx*32 + ty  ->  bank = (tx*32+ty) % 32 = ty
//   warp 里所有线程的 ty 是同一个值！
//   -> 32 个线程全撞在 bank ty 上 -> 32 路冲突 ✗
```

**写入没事，读出崩了。** 因为转置的本质就是换维度访问，而这一步正好把「分散」变成了「聚集」。

治法——**把数组宽度多加 1**：

```cuda
__shared__ float tile[32][33];      // 32*33 而不是 32*32

// 读出 tile[tx][ty]：字地址 = tx*33 + ty
//   bank = (tx*33 + ty) % 32 = (tx + ty) % 32
//   tx = 0..31 -> bank = ty, ty+1, ..., ty+31  -> 32 个不同 bank ✓
```

**加 1 个元素，每一行就相对上一行错开一个 bank**，原来「上下对齐」的列访问被打散成「斜着排」。看起来像玄学，上面两行算术就是它的全部道理。

这就是 Mark Harris《An Efficient Matrix Transpose in CUDA C/C++》里 `transposeNoBankConflicts` 版本的**全部改动**。

## 8. 怎么用这个模型判断自己的 kernel

遇到一个 kernel，按顺序问四个问题：

| 问题 | 涉及层级 | 怎么判断 |
| --- | --- | --- |
| **① SM 点亮了吗？** | SM | `gridDim × blockDim` 要远大于 SM 数 × 每 SM 可驻留线程。本机：≥ 14 × 1024 = 14336 线程才满 |
| **② 够不够盖住延迟？** | warp | 计算受限的 kernel 要 ≥ 8 个 warp/SM（§3.2 实测 4 个只有 78.2%）；**访存受限的要往满占用率去**（因为访存延迟几百周期，比 ALU 长一个数量级） |
| **③ 显存访问合并了吗？** | warp | 相邻线程的地址差是不是 1？不是就要考虑共享内存 |
| **④ 共享内存有没有 bank 冲突？** | warp | 用 §7.6 的算法算一遍 |

**判断 ② 的关键**：先问「这个 kernel 卡在哪」。

- 卡在 ALU（有长的依赖链）→ **8 个 warp/SM 上下就够**（§3.2 实测），再往上加意义不大
- 卡在访存（大量 load/store）→ 需要往满占用率去，因为访存延迟比 ALU 长一个数量级

这条正好解释了两个实测现象的差异：

| 测量 | 结果 | 原因 |
| --- | --- | --- |
| `<<<14, 256>>>` vs `<<<14, 1024>>>`（纯 ALU 循环） | 一样快（21.4 vs 21.3 ms） | ALU 依赖链的延迟只有几周期，8 个 warp 就盖住了 |
| `saxpy <<<14, 256>>>` vs `<<<4096, 256>>>`（访存受限） | 慢 1.57 倍（139.2 vs 88.7 µs） | 访存延迟几百周期，256 线程/SM 根本盖不住 |

## 10. 还没搞清楚的

诚实记录几个悬而未决的点，避免以后当成已知结论用：

1. **SM 内部到底几个子分区。** 实测只能确定「每 SM 64 个 FP32」。吞吐扫描区分不了「4×16」和「2×32」，因为它们预测完全一样。表格里写的「4 分区 × 16」是 Turing 的官方布局，不是测出来的。
2. **`%nwarpid` 的含义。** 实测恒返回 32（= 每 SM 最多 warp 数），不是「当前驻留了多少 warp」。文档描述含糊，暂按「上限」理解。
3. **block 落位的规律。** 观察到 0→SM0、1→SM2、2→SM4、3→SM6 这种跳着分（偶数号 SM），但样本太少，不知道是不是稳定规律。
